An essay · July 2026

How software gets built is changing faster than how we manage it.

Five years ago, AI in development meant autocomplete. Today, agents plan work, write code, review it, test it, and come back with a pull request. This is a short tour of that shift: where it came from, what it has genuinely solved, and why the next gains will come from platforms.

A note before we begin: I write this as an outsider looking in. Everything here comes from public research and engineering blogs, plus my own hands-on building with these tools. The teams running engineering systems inside large companies know things I can't see from here. Consider this a point of view I'd be eager to pressure-test on the inside.

Chapter 1

Four waves in five years

2021–2022, autocomplete. GitHub Copilot launched as an "AI pair programmer." It suggested the next line of code inside a single file. Useful, narrow, and easy to ignore.

2022–2023, chat. ChatGPT and Copilot Chat turned code into a conversation. Developers could paste an error and ask why it was happening, in plain English, without leaving the editor.

2023–2025, agents in the editor. Tools like Cursor and Copilot's agent mode began planning work, editing across many files, and running commands while the developer supervised in real time.

2025–2026, delegation. Claude Code, OpenAI Codex, Google Jules, and GitHub's coding agent now take a ticket, work in the background, and return a pull request for human review. The unit of work shifted from a suggestion to a task.

Chapter 2

Coding was just the beachhead

Software isn't just written. It's planned, designed, reviewed, tested, built, deployed, operated, migrated, and documented. AI is now touching every one of these phases, unevenly. An honest ledger of the lifecycle looks like this:

  • Measured wins published: test generation, large mechanical migrations, and first-pass code review. Airbnb converted roughly 3,500 test files in six weeks, work estimated at a year and a half. Google reports 80% of code changes in its internal migrations are now AI-authored. First-pass review arrives in seconds instead of hours.
  • Useful drafts, human judgment still required: planning, coding itself, build triage, incident response, documentation. Planning tools decompose epics but can't decide what's worth building. Incident tools summarize outages in minutes but their root-cause guesses still need verification. Coding is split: big gains on unfamiliar or boilerplate work, murkier results for experts deep in mature codebases.
  • Still open: architectural tradeoffs that depend on organizational context, deployment and config safety where a wrong change has a blast radius, and the deepest one: trusting an agent's output without a person re-verifying everything.

The green cells share one trait: a machine can verify the output.

Chapter 3

The uncomfortable part

Developers using these tools feel dramatically faster. The measured picture is murkier, and the gap between the two is where the interesting product problems live.

The METR trial · 2025
+20%how much faster developers believed they were
−19%how much slower they actually were, measured

In a randomized trial, experienced engineers working in codebases they knew well were 19% slower with AI assistance, while believing they had been about 20% faster. The perception gap is the finding: self-reported speedup can't be trusted as a metric.

Google's DORA research found the organizational version of the same story: as AI adoption rose, teams pushed more code through the pipeline while delivery stability declined. Teams shipped bigger batches, and more of them broke.

What it means: code generation improved faster than verification. The bottleneck moved downstream, into review, testing, and trust. Any serious effort in this space has to attack the whole pipeline, because speeding up typing alone just piles work at the next gate.

Chapter 4

What the leaders are publishing

The companies publishing real numbers share a playbook: narrow agents pointed at verifiable work, with humans reviewing everything that lands.

Google

80% of code changes in landed internal migrations are AI-authored, with every change human-reviewed. Engineers report roughly half the total time on migration work.

Amazon & Airbnb

Amazon says its Java-upgrade agent saved the equivalent of 4,500 developer-years and ~$260M in annualized efficiency. Airbnb's test migration finished in six weeks instead of eighteen months.

Stripe & Meta

Stripe's internal "Minions" agents merge about 1,300 pull requests a week, kicked off from Slack or a ticket. Meta publishes its filters as candidly as its wins: most generated tests are discarded, and only the provably useful survive.

Spotify

87% of Spotify developers use AiKA, the AI assistant built into their internal portal, weekly. Portal plugins are now exposed as agent-discoverable tools, with policy enforced centrally. The developer platform is becoming the control plane for agents.

Chapter 5

Why the next gains come from platforms

Individual tools got the industry this far. But thousands of developers each wiring up their own agents produces duplicated effort, ungoverned access to code and credentials, and no way to measure whether any of it works.

The answer looks like the internal developer platforms that tamed cloud infrastructure, extended to agents:

  • Orchestration, so agents compose and reuse rather than reinvent.
  • Golden paths, so the well-instrumented route is also the easiest one.
  • A curated marketplace, so teams share agents instead of rebuilding them.
  • Governance, so an agent's access is brokered, scoped, and audited.

Measurement lives here too. Acceptance rate flatters the tool. The metrics that matter are outcomes: lead time, change failure rate, and where engineering hours actually go. Instrument the platform once, and every team gets truthful numbers for free.

Chapter 6

Three working hypotheses, held loosely

Hypothesis one

Make the safe path the fast path. Adoption follows convenience, every time. If the governed, instrumented route is also the easiest one, you don't have to mandate anything. I watched this play out firsthand consolidating 30+ internal tools into 8 workflows at Amazon: adoption hit 100% because the new path was simply better, and usability scores rose 78%.

Hypothesis two

Measure outcomes on a counterbalanced scorecard. Pair throughput with stability so a win on one can't quietly become a loss on the other. Track the gap between perceived and actual speedup directly, because the METR result shows it's real. I learned the hard way that a product without an agreed success metric stalls; the fix made measurement the first feature, and adoption followed.

Hypothesis three

Curate more than you build. The ecosystem will produce more agent capability than any single team can. The platform's leverage is discovery, quality bars, and trust, so a developer can adopt a shared agent with the same confidence as a standard library.

And the questions I'd ask first: where does agent output actually stall today: review, CI, or trust? Which workflows have the strongest verification oracles, making them ripest for delegation? What does the cost curve look like at full scale, and where do smaller, cheaper models fit? The answers live inside, with the teams and the telemetry.
