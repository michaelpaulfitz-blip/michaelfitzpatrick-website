Project-Level Best Practices

Project memory (CLAUDE.md) & project settings — the full guide

TL;DR: The feature is called project memory — a CLAUDE.md file at the repository root (or .claude/CLAUDE.md), loaded automatically into every Claude Code session in that project. Commit it to git so it's shared. It holds instructions Claude follows; its sibling .claude/settings.json holds machine-enforced configuration (permissions, hooks, env vars). The global ~/.claude/CLAUDE.md covers personal preferences across all projects; project memory loads after it and overrides it where they conflict.

The file landscape

  • CLAUDE.md (project root) — team-shared project memory: build/test commands, conventions, architecture pointers, workflow rules.
  • CLAUDE.local.md — gitignored personal overrides for this project (sandbox URLs, local shortcuts).
  • ~/.claude/CLAUDE.md — global personal instructions for every project.
  • @file imports — inside CLAUDE.md, @path/to/file pulls another file into context at session start (e.g. @README) instead of duplicating its text.
  • .claude/rules/*.md — path-scoped rules with YAML frontmatter (paths: src/**/*.ts) that load only when Claude touches matching files, saving context.
  • .claude/settings.json / settings.local.json — enforced settings: permission allowlists, hooks, environment variables. Local overrides shared; add local to .gitignore.
  • Project-scoped skills and agents live under .claude/skills/ and .claude/agents/.

Writing an effective CLAUDE.md

  • Keep it under ~200 lines. It's loaded into every session's context — bloat costs tokens and reduces adherence. Split growing detail into path-scoped rules.
  • Structure with headers and bullets; one entry per concept, no repetition.
  • Be concrete enough to verify: "run npm test before committing" beats "test your changes."
  • Include: build/test commands, style specifics, project-structure pointers, workflow rules, gotchas and anti-patterns, decisions that differ from defaults.
  • Exclude: long prose and tutorials (use skills for repeatable workflows), anything derivable from the code, README duplicates (import instead), personal preferences (those go global or local).
  • Iterate: when Claude gets something wrong twice, add a rule; trim stale rules regularly; watch for conflicting instructions across files.
  • If something must always happen at a specific moment (e.g. lint before every commit), use a hook in settings.json — hooks execute deterministically; memory is guidance Claude follows but the harness doesn't enforce.

Project settings (.claude/settings.json)

  • Commit team-wide permission allowlists (pre-approving safe, frequent commands) so sessions prompt less; keep personal exceptions in settings.local.json.
  • Hooks automate lifecycle actions (pre/post tool-use, session start) for enforcement that shouldn't depend on Claude remembering.
  • Precedence, high to low: managed (org) → command line → local settings → shared project settings → user settings.

Useful commands

  • /init — auto-generate or improve a CLAUDE.md by scanning the codebase.
  • /memory — browse and edit all memory files.
  • /context — verify which memory files loaded this session.
  • /doctor — audit setup; flags bloated or redundant memory content.
