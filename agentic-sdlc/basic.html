AI Development on a Core Engineering Platform

Over the past five years, AI in development went from autocomplete to agents that take a ticket, write the code, review it, run the tests, and hand a person a pull request to approve. This is a walk through what that actually changed across the software development lifecycle, what it hasn't, and where the next real gains come from: the core engineering platform every developer builds on.

Where this comes from, in a sentence. I wrote it to work out my own thinking on where AI dev tooling is going and what a platform team should do about it. It leans on public research, engineering blogs, and what I've built with these tools myself. The people inside Twitch's Platform Core Engineering org know things I can't see from the outside, so treat this as a conversation-starter — I'd expect a good chunk of it to change once I hear what you already know.

Chapter 1

Five years, five waves

2021–2022, autocomplete. GitHub Copilot

GitHub Copilot suggested the next line of code inside a single file. It was a helpful convenience that a developer could accept or ignore.

2022–2023, chat. ChatGPT (OpenAI)Copilot Chat

ChatGPT and Copilot Chat let developers ask questions in plain language. A developer could paste an error and get an explanation without leaving the editor.

2023–2025, agents in the editor. CursorCopilot agent mode

Cursor and Copilot's agent mode began planning changes, editing across multiple files, and running commands while the developer supervised in real time.

2025, delegation. Claude CodeOpenAI CodexJules

Claude Code, OpenAI Codex, Google Jules, and GitHub's coding agent now accept a ticket, work in the background, and return a pull request for a human to review. The unit of work became a task rather than a keystroke.

2026, platforms and control planes.

The frontier now is less about any single agent and more about running lots of them as a governed capability. Microsoft's Agent Framework hit general availability in April 2026, and platform teams across the industry are wrapping orchestration, governance, and a marketplace around agents so thousands of developers can use them safely instead of each wiring up their own.

Chapter 2

Coding was only the beachhead

A typical delivery pipeline moves through planning, design, coding, review, testing, build, deployment, operations, migration, and documentation. AI tooling has reached all of these stages. It has helped some of them a great deal more than others.

  • Where the wins are measured: test generation, large mechanical migrations, and first-pass code review. Airbnb converted about 3,500 test files in six weeks, a project it had estimated at a year and a half. Google reports that 80 percent of code changes in its internal migrations are now AI-authored. First-pass review that once waited hours now arrives in seconds.
  • Where AI drafts and humans decide: planning, coding itself, build triage, incident response, and documentation. Planning agents decompose epics but do not decide what is worth building. Incident tools summarize an outage in minutes, but their root-cause guesses still need to be checked. Coding help is uneven, with large gains on unfamiliar or boilerplate work and weaker results for experts inside a mature codebase.
  • Where the problems remain open: architectural tradeoffs that depend on organizational context, deployment and configuration safety where a wrong change has a real blast radius, and trusting an agent's output without a person re-verifying it.

The stages in the first group share one property: a machine can check the result against tests.

Chapter 3

Perceived speed and measured speed diverge

Developers using these tools report feeling much faster. The measured results are less clear, and the gap between the two is where the interesting product problems sit.

The METR trial · 2025
+20%how much faster developers believed they were
−19%how much slower they actually were, measured

In a randomized trial, experienced engineers working in codebases they knew well were 19 percent slower with AI assistance, while estimating afterward that the tools had made them about 20 percent faster. This is why self-reported speedup cannot be used as the measure of success. (METR)

Google's DORA research found a matching pattern at the organizational level. As AI adoption rose, teams pushed more code through the pipeline while delivery stability declined. Larger batches shipped, and more of them broke. (DORA 2025)

What it means for a platform: generation improved faster than verification, so the bottleneck moved downstream into review, testing, and trust. A platform that speeds up writing without speeding up verification simply moves the pile of work to the next gate. The whole pipeline has to be addressed together.

Chapter 4

What the leaders have published

The companies reporting real numbers follow a common pattern: narrow agents pointed at verifiable work, with humans reviewing whatever lands.

Google

80 percent of code changes in landed internal migrations are AI-authored, with every change human-reviewed, and engineers spending roughly half the time they used to. (Google Research)

Amazon & Airbnb

Amazon reports that its Java-upgrade agent saved the equivalent of 4,500 developer-years and about 260 million dollars in annualized efficiency. Airbnb migrated roughly 3,500 test files in six weeks against an estimate of a year and a half. (AWS, Airbnb)

Stripe & Meta

Stripe's internal agents merge about 1,300 pull requests a week, started from a Slack message or a ticket. Meta publishes its filters as openly as its wins: most generated tests are discarded, and only the ones that provably add coverage are kept. (Stripe, Meta)

Spotify & Backstage

Spotify's internal developer platform, built on Backstage, the most widely used internal-developer-platform framework, now exposes plugins as tools any agent can discover, with the platform brokering permissions. The developer platform is becoming the control plane for agents, and it is the model the most advanced engineering organizations are converging on. (Spotify, Backstage)

Chapter 5

Why the next gains come from a platform

Individual tools got the industry this far. But thousands of developers each wiring up their own agents means duplicated effort, ungoverned access to code and credentials, and no real way to know whether any of it is working.

It looks a lot like the internal developer platforms that tamed cloud infrastructure, aimed now at agents:

  • Orchestration, so agents compose and reuse rather than reinvent.
  • Golden paths, so the well-instrumented route is also the easiest one.
  • A curated marketplace, so teams share agents instead of rebuilding them.
  • Governance, so an agent's access is brokered, scoped, and logged — down to the MCP tools it can call and the context it can see.

This is the ground a core engineering platform covers, from source control through build to deployment, and it serves every developer persona, not just app engineers: ML and MLOps, data science, whoever else builds here. Measurement belongs here too. Acceptance rate flatters the tool; the numbers that matter are outcomes: lead time, change failure rate, whether developers adopt what you ship, and where engineering hours actually go. Instrument the platform once, and every team gets numbers they can trust.

Chapter 6

How I would approach the product role

Start from the developer's problem. On this platform, developers are the customer, and the only score that counts is whether they adopt what I ship, lean on it, and tell other teams to use it. So I would spend the early weeks sitting with the engineers and codebase owners who live in these tools, finding where their day actually stalls, and weighing that against where the technology is clearly headed. You need both: the humility to hear the pain, and the spine to still make a call on direction.

Set the goals and define success. I would nail down what we are trying to move, and how we will know, before writing a line of code. Outcome metrics, not acceptance rate: lead time, change failure rate, adoption, and the share of engineering time going to new work instead of toil. Pick the scoreboard early and the platform stays honest as it grows.

The hardest part is alignment. A lot of this job is not building; it is alignment. I would work directly with the principal engineers and engineering managers who own the surrounding systems, get the dependent teams pointed the same way, and referee the competing priorities that always surface when several strong teams each show up with their own approach. Most of that comes down to making the technical tradeoffs legible, so people argue about the right things and then commit. Early on I would get the internal engineering groups aligned first, then pull the broader customer teams in once the core actually works.

Then execute, measure, and iterate. Then it gets tactical: sequence the roadmap, ship in small increments, watch the metrics, adjust. I would own launches end to end — the migration path off the old thing, the docs, the adoption push — because a capability nobody moves onto is the same as one you never shipped. Start with a few early-adopter teams, widen along the golden paths, and keep the loop with developers tight enough that the platform keeps up with what they actually need.

Chapter 7

Four Working Proposals

Proposal one

Make the safe path the fast path. Adoption follows convenience. If the governed, instrumented route is also the easiest one, mandates become unnecessary. I saw this directly when I consolidated more than 30 internal tools into 8 workflows at Amazon: adoption reached 100 percent because the new path was simply better to use, and usability scores rose 78 percent.

Proposal two

Measure outcomes on a balanced scorecard. Pair throughput with stability, so a win on one does not quietly become a loss on the other, and put adoption right next to them — a tool nobody uses is not a win at any speed. Track the gap between how fast developers feel and how fast they actually are, because METR shows that gap is real. Decide what success looks like before shipping, or the platform drifts toward measuring activity.

Proposal three

Converge on one platform instead of ten. The win here is not building every capability yourself. It is pulling the efforts already scattered around the company into one platform and standard people actually want to adopt. Curate more than you build, so the whole org moves together instead of four teams each shipping their own half-finished version.

Proposal four

Route by cost, and hide it from developers. You do not need a frontier model for everything. More and more large eng orgs are standing up their own GPUs — NVIDIA H200s and the like — to run open-weight models on the easy tasks, and reporting AI-dev cost cuts of around 70 percent. The whole trick is in the product design: the routing has to be invisible. Make the cheap model an opt-in and nobody picks it, because no one trades quality for a budget line they cannot even see. So the platform quietly sends each task to the cheapest model that can do it well, and saves the frontier ones for the work that genuinely needs them.

And the questions I would ask first: where does agent output actually stall today — in review, in CI, or in trust? Which workflows have the strongest verification, making them the safest to delegate? What does the cost curve look like at full scale, and where do the smaller, cheaper models earn their place? I cannot answer these from the outside. They live inside the team and the telemetry, which is exactly the conversation I want to have.
